Shapes that are no longer supported, or that now fail the build:

- **React's classic JSX runtime** isn't supported with automatic code splitting, nor in files Start compiles: a split chunk with JSX has no `React` in scope and throws `React is not defined`, and when Start removes code, an `import React` that only a removed type annotation used goes too. Use the automatic JSX runtime.
- **A second call of a route file's route constructor** (`createFileRoute`, or the root constructor, also through the router's namespace: `Router.createFileRoute(…)`) fails the build at that call, on every host, whatever its options hold. Write one call per file, bound to `Route`.
- **A `createFileRoute` imported through a module of the app that re-exports the router's**, from another package or from a subpath isn't recognised: the route is served as written and isn't split, and under TanStack Start its `server`, `ssr` and `headers` options ship to the client, with no warning. Such a Start build used to fail. Import `createFileRoute` from the framework's router package.
- **A server function its module doesn't create exactly once, when it loads,** fails the build in every environment, naming the position, with "define it at the top level": under a condition (a ternary's branch, the right side of `&&`, `||` or `??`, after `?.`, a destructuring default), in a loop, `if`, `try`, `switch` or block, inside any function body (a component, an IIFE, a method, an accessor, a default parameter), in a class instance field, or in a Vue `<script setup>` block, whose code runs inside the component's setup function. One that reads a local of the function around it is reported at the local. Define it at the module top level and pass what it needs in its input. These failed Vite builds before too (`createServerFn must be assigned to a variable!`), except a server function in `<script setup>`, which built and failed when called (`Server function module export not resolved`); on Rsbuild, one in a function body built and shipped its handler to the client.
- **Server code passed by a name its module assigns elsewhere** fails the build in every environment, and the module's compile in development: a server function's `.handler()` or `.validator()`, a middleware's `.server()` or `.validator()`, an isomorphic function's `.server()`, `createServerOnlyFn()`, and a route's `server` option (`server: { handlers: { GET: get } }`, also through `createHandlers({ GET: get })`, a spread or a `middleware` array) or `headers` option, or its `ssr` option, given a binding the module assigns again outside server code (`let selected = a; createServerFn().handler(selected); selected = b`, also through a cast, `selected = wrap(selected)`, a conditional write such as `if (!selected) selected = …`, or a write in a function), whatever else reads or exports it. The client code can keep the assignments with what they read, so server code can ship to the browser (on `main` it could, and it ran there in development). Not refused: one only server code assigns. Pass it written in place, or define it once with a `const` (`const selected = wrap(async () => …)`, `const selected = condition ? a : b`).
- **A Vite build that builds the server environment before the client** (a plugin's `buildApp`, a hand-written `createBuilder()`) fails with a message saying to build the client first: the server's list of callable server functions comes from the client build. Start's own `buildApp` is unaffected.
- **A `virtual:` module with a `server-only` marker** (an id without the `\0` prefix) fails a Vite build, naming the module. Move the code into a file.
