Import protection:

- **Exempt importers get the real module.** A module that `exclude` or `ignoreImporters` exempts gets the real module of a denied file it imports plainly; it got the mock. An importer outside the scope (`include`, `srcDirectory`) still gets the mock, and a build now warns once about each denied file it mocks whose every importer is unchecked, naming the file, what denies it, its importers and the fix. The warning isn't a violation: `onViolation` isn't called and `'error'` doesn't fail the build.
- **Importers that disagree fail the build**, on Vite and Rsbuild, under both behaviors: one importer needs a denied file as it is (an exempt plain import, or one `allowImport` allows) while a checked module reaches the file itself (a pattern import such as `import.meta.glob`, or an import another plugin added). The error names the file, each importer and the two fixes: leave the file out of the pattern, or narrow the exemption or `allowImport`. Dev servers print it and keep serving.
- **Verdicts come after tree-shaking:** a build reports only what is in its final client bundle: a mock in one of the bundle's chunks is a violation, one the bundler dropped reports nothing. An import of a denied file that tree-shaking removes no longer fails the build, on Vite and Rsbuild, whatever the file runs at its top level (the client gets the mock, which runs nothing). A bare import (`import './x.server'`), a kept `import()` or `require()` that reads nothing, and an import of type names that `verbatimModuleSyntax` keeps are violations where the build keeps their importer, whatever the tree-shaking options; so is a client entry's own `export {} from '@tanstack/react-start/server-only'`, on Rsbuild too (it built and ran the entry). A denied file that code the compiler does not read imports (a package module, another plugin's import) is mocked as a whole under its package's own `sideEffects`: an unused import of it there is a violation, as on main.
- **Pattern imports:** on Rsbuild, a denied file reached through a template-literal `import()` or `import.meta.webpackContext` is reported (an `'error'` build fails), and the Vite dev server reports the pattern imports it mocks. Both mocked them silently.
- **React Server Components:** a `'use client'` module that a server component imports is a client reference where server components render (Vite's `rsc` environment, Rsbuild's RSC layer): a `.client.tsx` component that a server component rendered was replaced by its mock there, and the page failed to render it. The server component's import of it is how SSR, which renders the component, gets it: when a server rule denies the file, `allowImport` is asked about that import and `onViolation` reports it with `info.env === 'rsc'`, the server component as `importer`, the specifier as written and its position, on Vite and Rsbuild (Rsbuild called it `ssr`; for a marker, Vite reported the marker's import inside the component, in `ssr`). The answer decides what SSR gets: the real component, or its mock and the report (an `'error'` build fails); an exempt server component gives SSR the real one. Its report suggests renaming the file without `.client` (or removing its marker) if it can render on the server, or `<ClientOnly>` inside another `'use client'` component: a `<ClientOnly>` in the server component doesn't keep it out of SSR.
- **Rsbuild with RSC: the RSC layer is the `rsc` environment.** `onViolation` and `allowImport` get `info.env === 'rsc'` for a module of the server compiler's RSC layer (server components, server functions' handlers), as on Vite; it was `'ssr'`, the name of SSR's modules too. Match `info.envType === 'server'` for both. The rules that apply there are unchanged (the server rules). `allowImport` is asked once per import and environment, so an import that a file of both layers makes is asked about for `ssr` and for `rsc`, as on Vite.
- **Rsbuild dev and watch builds serve what a fresh build serves.** A denied file is real exactly when an exempt or allowed import arrives at it from a module the app reaches without a denied module served as its mock. The app is what the compilation holds by itself: its entries and includes, however a plugin adds them (`compilation.addInclude` with or without an entry included). So an exempt importer that an edit takes out and puts back gets the real module again (`vite build --watch` too), a denied file in a cycle with its exempt barrel (or a barrel whose import of it `allowImport` allows) no longer keeps itself real once only a checked import reaches it, one edit that flips two denied files serves both as a fresh build does, and a denied file in a layer of your own that the build only finds while building another one gets its real module. A compilation whose module imports change between two builds of the same source names the history of that module (or the server functions, with their files, of a resolver that goes back to an earlier content): a build fails instead of serving it otherwise than its source asks for, and a dev server warns (the next edit starts again). A denied file only a worker plugin's child compiler builds is reported under `behavior: 'error'` in dev too. Every compilation settles the modules it builds, including a worker plugin's child compilation and a module a plugin adds late (a Module Federation shared provide): a denied file that a child compilation only reaches through a checked import (a context) fails the build as a denied import there does, also when the child's exempt entry names it in an import the bundler drops; and a provided module's exempt import of a denied file gets the mock in a cold build as in a cached one, as `main`.
- **Asset queries:** on Vite, `?raw` of a file with a `server-only` marker gives the client the mock; its text shipped.
- **Rsbuild:** a module that a worker plugin builds in a child compiler (`worker-rspack-loader`, workbox) is checked: a denied import there fails the build at the import, whatever the `behavior` (a child compiler can't load the mock), and is reported to `onViolation`; it was mocked silently.
- **Reports:** Vite builds report every violation, not only the first. Mock mode says "Import mocked". A pattern import's report names the pattern and its position and suggests a `!` exclusion. On Rsbuild, traces start at the app's own first file instead of Start's client entry. The suggested fix fits the import: `<ClientOnly>` for a component rendered on the server (for a route option's component, a wrapper that passes the router's props on: `errorComponent: (props) => <ClientOnly fallback={...}><Oops {...props} /></ClientOnly>`, after `const Component = …` when the value is no component's JSX tag, such as `chart` or `Screens['chart']`), `createClientOnlyFn` for a function. A trace with no file of the app is left out. A marker violation gives the position of the marked module's marker import (`src/count.ts:3:8`). In production builds, a mocked value reports its use at runtime too.
