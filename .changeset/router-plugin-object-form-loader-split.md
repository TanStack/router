'@tanstack/router-plugin': patch
---

Loader code splitting works with the object form of `loader` (`{ handler, dehydrate, hydrate, staleReloadMode }`). Only `handler` moves to the loader chunk; the other keys stay in the route file, where the router reads them without loading the chunk. Before, an object-form loader in a `loader` split group failed the build with "Unexpected splitNode type: ObjectExpression".

Also in the loader split: a `handler` written as a getter or setter leaves the loader unsplit; an imported handler keeps its import when another key of the route still uses it (`hydrate: ({ data }) => fetchPosts.parse(data)`), and the import is removed only when nothing else references it; `satisfies`, `!` and `<T>` around the loader function no longer break the loader chunk, and the handler may sit behind these wrappers, `as` or parentheses.

An object-form loader held in a `const` of the same file (`const postsLoader = { handler, dehydrate: true }` and `loader: postsLoader`) is split by its `handler` too; before, the chunk exported the whole object and calling the loader threw a TypeError. The loader is left unsplit when that variable is exported, reassigned or read anywhere besides `loader`, types aside (another option such as `head` calling `postsLoader.handler(ctx)` gets the function it wrote, not the lazy wrapper); when a split option such as `component` reads it, the object moves to the shared module together with what its handler uses, so the route and the chunk read one object and one copy of its state instead of each initializing their own. A `handler` method that uses `super` stays in its object. `deleteNodes` strips such a `const` as it strips an inline literal, in every module that keeps it: the route file, the shared module, and a chunk that keeps a copy for top-level code reading it. A binding exported with a specifier (`export { loadPosts }`) counts as exported: the option is left unsplit with the usual warning, for the function form, the object form and components alike; before, the specifier was overlooked and the reference module lost the declaration. A loader or component that is a fallback literal under a TypeScript wrapper (`loader: undefined as any`, `component: null!`) is kept in place like the bare literal. An imported component keeps its import in the route file while another option still reads it (`head: () => ({ meta: [{ title: PostsComponent.title }] })`); before, the import was removed and the option threw a ReferenceError. A side-effect import of the component's module (`import './posts-component'`) is no longer removed from the route file either.

The keys `deleteNodes` removes no longer count when bindings are shared between the route file and its chunks: a helper only a removed key used (`dehydrate: ({ data }) => toWire(data)` on the client) leaves the shared module with its import, and a helper the handler shares only with a removed key goes to the loader chunk instead of a shared module. Route options passed as `{ ... } satisfies RouteOptions` or `as`, inline or through a variable, are split and stripped like a bare literal; before, they were left untouched. A split component behind `satisfies` or `!`, and a handler or loader that is a member or other expression (`handler: api.list`), no longer fail the build with "Unexpected splitNode type". An exported component behind `as`, `satisfies` or `!` stays in the route file like the bare identifier, with the same "will not be code-split" warning; before, `as` split it. A split component that top-level code also reads (`PostsComponent.displayName = 'Posts'`) keeps its declaration in the route file; before, the declaration was removed and loading the route threw a ReferenceError. An exported loader or component that an option left in the route file also reads is no longer moved to the shared module, since the route file keeps it anyway. A split loader, handler or component that is a call with type arguments or annotated parameters (`makeLoader<Post>('posts')`, `wrap((name: string) => name)`) keeps them in the chunk; before, `f<T>(x)` became a comparison and an annotated parameter failed the build.
