Server functions:

- **Written in any position evaluated once at load.** A server function that isn't a top-level declaration builds when its expression runs exactly once, unconditionally, when the module loads: an object or array entry, a call argument, `export default`, an assignment, a member's object (`.bind(null)`), a class's static field or block, a top-level `await`. It is created at its place in the module's order. These weren't compiled, on Vite and Rsbuild alike: in a module whose only Start function is `createServerFn`, the build passed, shipped the handler to the client and registered no endpoint; in a module that also uses `createMiddleware`, `createIsomorphicFn`, `createServerOnlyFn` or `createClientOnlyFn`, the build failed (`createServerFn must be assigned to a variable!`), except for a member's object (`.bind(null)`), which built and shipped the handler. Other positions fail the build (see the unsupported shapes changeset).
- **One instance per server function** (SSR as the provider): a handler shares its module's state and classes with the rest of the module, so `instanceof` holds and the state the module writes is what the handler reads (#8656). Server code that imports a server function calls it directly (#7213, #8731), also one no client module imports, which failed with `Server function info not found`. A handler, its validator and what only they use still load on the first call; a handler that reads or writes its module's state at load, or one in a module with top-level `await`, loads with its module.
- **Chains of any length on Rsbuild:** a server function that only another one's handler imports is found however long the chain (each is found by building the one before); a build with more than eight such links answered `Server function info not found` for the ninth.
- **Recognised by binding** through re-exports, namespaces, aliases, the app's factories and stored builders, whatever the formatting (#7280). `createServerOnlyFn(…)` passed to `.handler()` works (#8446). A handler that is itself a `createClientOnlyFn(…)` throws when called (`… can only be called on the client`); the client implementation ran on the server.
- **HTTP calls:** a production build answers an HTTP call by id only for a server function the emitted client bundle still calls, on Vite and Rsbuild, with and without RSC. A server function private to a module the client imports (a helper only another handler calls) answered too, because the client's compile referenced it before tree-shaking dropped it. An exported server function the client never uses, in a module it imports, now leaves the client bundle and isn't callable either (Vite, except with `build.minify: 'esbuild'`; Rsbuild, except with `output.minify: false`): its client stub is one call that bundlers drop when its value is unused, while the code of its chain (options, middleware arguments) still runs. With those two settings the bundler keeps the stub, so the function stays in the client bundle and callable, as before. Server code still calls both directly. A server function that reaches the browser only as data (a loader returning it) is no longer callable over HTTP: reference it from client code. With a custom `serverFns.generateFunctionId`, the build no longer looks for the custom id's text in the client bundle (a string of the app equal to an unused function's id made it callable): each client stub passes a build token to the client RPC (`createGatedClientServerFn` of the new `client-rpc-gated` subpath, which stores it on the RPC, never sends it; an app without a generator imports nothing of it, and its client output is unchanged), and the token decides. It costs 13 to 14 bytes gzipped per server function the client keeps, the shared helper included (71 such functions: +0.9 kB on Vite, +1.0 kB on Rsbuild), in apps that set a generator only; ids, URLs and `serverFnMeta.id` are unchanged. A custom minifier must keep the stub's string arguments. The dev server still answers the others, and may warn when it has compiled no client code calling the function yet (not for an unused export of a module the client imports); the warning is a hint, not the production check.
- **Ids** keep their formats: the default id, the `functionName` a custom `serverFns.generateFunctionId` receives, `serverFnMeta.name` and the manifest's quoting, so custom ids stay the same. Ids a custom `generateFunctionId` makes collide across files get their `_1`, `_2` suffixes in file path order (functions client code references first), on Vite and Rsbuild. The deprecation warning for a custom id with `%` or another character URLs allow, which only the Vite plugin printed, is printed on Rsbuild too. A server function that isn't declared as a variable takes the name it is assigned to (an object property, a class field), `default` for `export default`, and `fn` otherwise.
- **Kits that list Start under `dependencies`** (instead of `peerDependencies`) are bundled on the Vite server and compiled, like peer-dependent kits; their server functions returned `undefined` during SSR. Like peer kits, they're now excluded from Vite's dependency optimizer, so `vite dev` serves them unbundled: if such a kit or its dependencies are CommonJS, add them to `optimizeDeps.include` (`'kit > dependency'` for a nested one). A library the app doesn't list in its `package.json` isn't bundled this way: on Vite its server functions throw during SSR (HTTP 500), so declare it.
- **`vite build --watch`:** the server builds once the client's first build is done, so the first build answers server function calls (none answered before); a server function the client stops importing is no longer callable after the rebuild; and a rebuilt server's documents load the client's latest build. On Rsbuild (`rsbuild build --watch`), an edit that removes a module's only server function removes it from the rebuilt server too; the rebuilt manifest still listed it. The two watchers coordinate through a file in a per-run directory under the system's temporary directory: a `build.watch.exclude` matching that directory isn't supported, and a temporary directory that can't be used leaves the build working, with a warning that says to fix it or set `TMPDIR`.
- **Vite dev:** a request for a server function the dev server hasn't compiled yet (a page left open across a restart) compiles the file its id names when that file, with symlinks resolved, is inside the app's `srcDirectory`, outside `node_modules` and allowed by `server.fs` (#8447). Any other id the dev server hasn't registered is refused with `Invalid server function ID`, as before. A server function an edit removes answers `Invalid server function ID` instead of a 500 `TypeError`.
- **Client route tree:** on Rsbuild, server-only routes are pruned from it (#8545). A route whose `server` handlers are in its route file and whose page is in its `.lazy` file (or a piece file) stays in it on Vite and Rsbuild; Vite pruned it, so client-side navigation to it failed.
- **Rsbuild:** a server function that only a worker built in a child compiler (`worker-rspack-loader`, workbox) calls is registered.
- **RSC:** on Vite, server functions in the app's own source (workspace packages included) that only a `'use client'` component imports statically are in the production manifest (#7943). Still missing, as before: one that a lazy `import()` from it loads, one of an installed package (call it from a route's `loader` as well: importing it from a server function's handler does not add it, and a call from such a handler answers `Server function info not found` too), one that the server resolves to another file than the client (a `react-server` condition), and one that only client-only code imports (a `<ClientOnly>` child, a `createClientOnlyFn` body, a `<Hydrate>` `fallback`). On Rsbuild, a server function that only a `'use client'` component of a server component imports (#7943) and one that only client-only code imports now answer, in a cold build, from the persistent cache and after a dev server restart: they answered `Server function info not found`. A server function whose handler renders a client component nothing else renders, which calls another one, is still missing on Rsbuild: the build succeeds, the component is missing from the client manifest, and the browser cannot show the result (React's `Could not find the module … in the React Client Manifest`). Render the component from server code the build reaches first, such as a server function a route's loader calls (web-infra-dev/rspack#16786). On Vite, a production build now fails for a server function the client calls that the RSC build does not provide (the cases above), naming each one and its file, with the way out for a file of the app (import it in a server function's module as well and use it in that function's handler) and for one of an installed package (call it from a route's `loader` as well): such a build succeeded, and the call answered `Server function info not found`. The dev server is unchanged. With RSC, a production build on Rsbuild builds only the server functions server code declares or the client's emitted code calls: one nothing calls, whose handler imports a package with only a `development` export, failed the build. `renderServerComponent` or `createCompositeComponent` outside a server function fails the build at the call; it built and threw at runtime (`… cannot be called on the client`).
