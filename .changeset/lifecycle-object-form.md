`context`, `beforeLoad` and `loader` accept an object form `{ handler, dehydrate, hydrate }` that controls what crosses the wire during SSR. The route `context` option and the `dehydrate` and `hydrate` keys are experimental: they may still change in a minor release before they are declared stable.

- `dehydrate: true` sends the result to the client, `dehydrate: false` keeps it on the server (the client re-runs the lifecycle during hydration), a `dehydrate` function sends a custom wire value and `hydrate` rebuilds the value on the client from it and the route's context. Both may be async; the awaited values are used in the types. Defaults: `context` is not sent, `beforeLoad` and `loader` are.
- During SSR hydration the client restores what was sent and re-runs what was not: `context` and `beforeLoad` route by route, then the loaders in parallel. A failure there (an error, a thrown `redirect()` or `notFound()` or one returned from `beforeLoad` or `loader`, a throwing `hydrate`) is not handled by hydration: the route is shown as pending and the normal client load after hydration runs the lifecycle's handler again and handles the outcome as a client navigation does (data, error, redirect or not-found). A route the server already rendered as an error or not-found, and the root route when it shows the not-found page, keep that result instead: during hydration only their `context` and the `hydrate` of sent results run there. A `beforeLoad` or `loader` result that was not sent is missing there in the browser, and a failure there makes nothing run again and leaves the result that failed missing. A lifecycle that the client re-runs during hydration and that fails there therefore runs twice on the client, side effects included. `hydrate` never shows an `errorComponent` or calls `onError` by itself. `dehydrate` and `hydrate` are transforms: a `redirect()` or `notFound()` thrown from `dehydrate` is an ordinary error of that match.
- `hydrate` requires `dehydrate` (`true` or a function); a `dehydrate` function requires `hydrate`. Key order is `handler`, `dehydrate`, `hydrate`, then `revalidate` or `staleReloadMode`; the parameters of the codec halves are inferred and must not be annotated. The pairing rules are type errors; the order and annotation rules are enforced by `@tanstack/eslint-plugin-router`.
- Client data is inferred from the client handler's result. `hydrate` must satisfy that type. With `createIsomorphicFn`, `dehydrate` receives the server handler's result. Different server/client shapes are allowed when the effective SSR policy rules out server rendering. A route that can render on the server requires its server result to satisfy the client type.
- SSR type checks resolve omitted options and undefined functional results against a registered `defaultSsr`, then apply parent restrictions. Explicitly enabling SSR under a disabled default still checks transported values for serializability.
- `context` is a cached lifecycle: it may be async, it runs once per match, serially and interleaved with `beforeLoad` (parent `context`, parent `beforeLoad`, child `context`, ...). It receives `deps` and not `search`. `context: { handler, revalidate }` re-runs it on `router.invalidate()`, as `revalidate: true` or as a function that receives `prev`.
- `context` receives TanStack Start's `serverContext` on the server, like `beforeLoad` and `loader`.
- On the server, a route with `ssr: false` (and every child route of a shell render) no longer runs `context`. Its server-side `head`, `scripts` and `headers` see only the inherited context, and an error thrown by that `context` now shows up on the client, which runs it.
- A server `context` that fails now leaves the match with the inherited context, as a failed `beforeLoad` does.
- `router.invalidate()` does not re-run a route's `context` unless `revalidate` is set. This matches the previous runtime behavior and corrects the docs, which said the context was recomputed.
- Loader results are serializability-checked again in Start apps with SSR, like `beforeLoad` results. Existing loaders returning `unknown`, `Record<string, unknown>` or class instances with methods surface type errors: return serializable data, set `dehydrate: false`, or register a serialization adapter. A `dehydrate` whose return type is `unknown` is rejected the same way. A `redirect()` or `notFound()` returned from `beforeLoad` or `loader` is not data and is not checked; before, a returned `redirect()` failed the `beforeLoad` check.
- Code-based `createRoute` routes get this check for the first time in Start apps, for `beforeLoad`, `loader` and a sent `context` alike. Before, they were never checked.
- `Route.options.beforeLoad` and `Route.options.context` may now be objects, so calling them directly (`Route.options.beforeLoad?.(ctx)`, common in unit tests) is a type error. Narrow with `typeof option === 'function'`, or call `option.handler`.
- A bare `vi.fn()` written inline as `context`, `beforeLoad` or `loader` is a type error now. Give it an implementation or a type argument (`vi.fn(() => {})`, `vi.fn<() => void>()`).
- With `dehydrate: false` or a custom `dehydrate`, the server handles rejections of promises in the top-level fields of a plain-object loader result, since the stream never sees them, and aborts the loader's pending work when the response is done (right away when `dehydrate` throws). Promises in arrays, class instances or nested objects get no such handler.
- A reused server router no longer renders loader data from its previous load.
- `router.invalidate()` and `onLeave` no longer throw for a match whose route `router.update` removed from the route tree.
- `DehydratedMatch.l` is typed `unknown`: a custom `dehydrate` may send any serializable value.
- The published types use TypeScript 5.4's `NoInfer`, so TypeScript 5.4 or newer is required (the docs said 5.3).
