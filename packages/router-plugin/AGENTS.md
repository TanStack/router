# Router bundler plugin

- Route splitting does what main's splitter does (R153, spec-main-splitting.md): wherever main's output builds and runs correctly, ours does too with the same runtime behaviour (the same options split or more, one instance where main has one, top-level code run once where main runs it once). Improvements over main wait until after #8817 (one by decision: a declaration already unused stays in the route module only and runs once). The route module loses only what the split made unused (used in removed code, a type use counting; nothing left reads it by value) and keeps its statements and exports and what they reach, and every class, enum and namespace, whatever names it (R163: main never removes one; only erasure does, when erased text names it and nothing staying reads it by value); an import nothing in the source references (bare and CSS ones included) moves to the shared module when the route module imports it, in source order, and otherwise stays (chunks load after the route module; React's classic JSX runtime is not supported with splitting); a chunk imports from it what main imports (`Route`, `export const|let|var`) and copies the rest with the statements, classes, enums and namespaces naming it, as main does; a binding only one chunk needs moves into it, and the names main shares (two options read them, a staying one included) are one shared module the route module and the chunks import. Tests assert values, identity and init counts, never placement.
- The options main splits are split. An option whose value is an exported binding stays in the route module and the build warns once, naming the file (main's warning); values main cannot compile into a chunk stay silently (`splitOnMain`, main's `compileCodeSplitVirtualRoute` cases), and so does one whose chunk would assign a binding it imports, or its copy of a binding another chunk copies too (`assignsWhatItImports`). Better than main, approved: a method option splits as a function expression with its body would (#8623), and a function expression or method using its own `this` or `super` stays, with a warning at the property (`ownThisOf`, #8688).
- Splitting and route HMR are planners on the shared compiler core: read [ARCHITECTURE-CODE-SPLITTING.md](ARCHITECTURE-CODE-SPLITTING.md) and the [core README](../router-utils/src/compiler/README.md). Planners only declare roots and edits; placement, dead-code removal and emission belong to the core.
- Generated route HMR code stays minimal: it calls the framework's `__tsrRouteHmr` from the dev-only `/hmr` subpath (`router-core/src/hmr.ts`) with static facts only (`file`, the module's id, which keys the runtime's one record per route file; the chunk and kept-reader calls pass it too). The runtime updates the route on every router of the page that holds a route this file evaluated to (never another file's route of the same id), rebuilds the route tree and refreshes active matches while preserving lazy-wrapper identities (React takes the new component after React Refresh's pass; Solid and Vue keep a component their refresh patches, and on Vite apply after `vite:afterUpdate`: the meta's `hot`). Keep that bookkeeping in the runtime, not in emitted code, and keep it out of production bundles.
- Tests run in two tiers. `test:unit` (fast tier, the inner loop) runs `tests/**` in process; a Vite dev server in middleware mode is allowed. `test:integration` (slow tier) runs `tests/integration/**`: every test that starts a real build (`build`, `buildAndRun`), an Rsbuild dev server or watch compiler, a child Node process or a browser page (`openRouteHmrPage`). Put such tests under `tests/integration/`; a file with tests of both kinds is split by test into files of the same name in both directories. Run both tiers before handing back.
- Test code-splitting changes by behaviour: load the route with `loadRoute` from `tests/route-app.ts` (a real Vite dev server with the public plugins; the route runs in a real browser page), and assert what users see (rendered output, loader results, init counts). Outcomes the bundler decides (dead code, chunk contents, `sideEffects` / `@__PURE__` hints) are asserted in a real build with `build` from `tests/build-harness.ts`, per bundler. What an opener opens closes when the test ends; the files of `integration-concurrent` open through the fixtures of `tests/test.ts`. Do not add output snapshots.
- Run behavioural tests for React, Solid and Vue through the `targetFramework` option of the test helpers.
- Test what the page shows after a route file edit with `openRouteHmrPage` (`tests/route-hmr-page.ts`): a real dev server with the framework's plugin, a real browser page and the real HMR client. Never copy bundler, HMR-client or React Refresh logic into tests. There is no in-process HMR model: test route HMR with `openRouteHmrPage`.
