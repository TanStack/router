# Router bundler plugin

- Code splitting must not change what a route does. The route module and its split chunks share one instance of every module-level value: `Route` and any state created at module load exist once, and every chunk sees the same object. Which bindings the splitter shares, copies or leaves in the entry is an implementation choice; tests assert values, identity and init counts, never placement.
- Every option configured for splitting must end up split. When a pattern the user can change prevents it, the option keeps working in the entry and the build warns once, naming the file and the option. When the limitation is ours, it is a bug to fix, not a warning.
- `handleRouteUpdate` is stringified and injected into app modules. Keep runtime dependencies inside the function or explicitly emit them; extracting a helper to plugin module scope breaks the generated function. `tests/handle-route-update.test.ts` executes that emitted code: it calls the emitted function with the route of an edited file and a live router.
- Route HMR rebuilds indexes, clears `resolvePathCache`, replaces lazy-chunk ownership, and refreshes active routes while preserving component identities (React, Solid and Vue). Keep these steps coordinated when adding derived state.
- Tests run in two tiers. `test:unit` (fast tier, the inner loop) runs `tests/**` in process; a Vite dev server in middleware mode is allowed. `test:integration` (slow tier) runs `tests/integration/**`: every test that starts a real build (`build`, `buildAndRun`), an Rsbuild dev server or watch compiler, a child Node process or a browser page (`openRouteHmrPage`). Put such tests under `tests/integration/`; a file with tests of both kinds is split by test into files of the same name in both directories. Run both tiers before handing back.
- Test code-splitting changes by behaviour: compile the route and load the emitted modules with `loadRoute` from `tests/regression-helpers.ts` (built on the module linker from `@tanstack/compiler-test-utils`), and assert what users see (rendered output, loader results, init counts). Outcomes the bundler decides (dead code, chunk contents, `sideEffects` / `@__PURE__` hints) are asserted in a real build with `build` from `tests/build-harness.ts`, per bundler. Do not add output snapshots.
- Run behavioural tests for React, Solid and Vue through the `targetFramework` option of the test helpers.
- Test what the page shows after a route file edit with `openRouteHmrPage` (`tests/route-hmr-page.ts`): a real dev server with the framework's plugin, a real browser page and the real HMR client. Never copy bundler, HMR-client or React Refresh logic into tests. There is no in-process HMR model: test route HMR with `openRouteHmrPage`. A unit test of `handleRouteUpdate` may call it with explicit inputs and a real router, but must not recreate hot contexts, disposal, module selection or framework refresh.
